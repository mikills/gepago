# Changelog

All notable changes to `gepago` will be documented in this file.

The project follows semantic versioning once public tags are published.

## v0.10.0

`Pipeline` can repeat a step, wrap its tools and read images. A bounded `Loop` runs a body step until a typed condition on the state holds. Tool middleware wraps every tool call that a pipeline run or an agent run makes through its own session. So you write limiting, logging, auditing and fallback once. User chat messages and `Predict` inputs carry PNG, JPEG and WebP images to the OpenAI, Claude and Google chat clients.

### Breaking changes

#### Pipelines and control flow

- A step can run a `Map`, `MapCollect`, `Parallel`, `WithPolicy`, `WithCache` or `WithAmendable` with its own `State`, through `Run` or `RunCandidate`. The composite now gives the steps it runs only the keys that `State` exposes. Those are the step's declared reads and the declared writes that the step has set. Before, they read every key in the run's state, and a key that the step had set showed its old value. `WithCache` builds its key from the same keys. A `Map` or `MapCollect` also reads its items key only when that `State` exposes it. So a step that runs one without declaring the items key now fails with `state key "words" is missing`. A pipeline that runs them as its own steps sees no change. Declare the key as a read of the step that runs the Map, the Parallel or the wrapper.
- `WithPolicy`, `WithCache` and `WithAmendable` that a caller runs with `Run` or `RunCandidate` now return the wrapped step's error as a `StepError` that names the step. `Parallel` does the same for its steps. So `errors.As` finds that `StepError` first. A pipeline that runs the wrapper as its own step returns the same error as before. A step with another name that calls the wrapper's `Run` now gets the `StepError`. `pipeline step "outer": flaky` then becomes `pipeline step "outer": pipeline step "fails": flaky`. A step with the wrapped step's name that runs in its own execution gets the error as it is. A decorator that embeds the wrapper and keeps its name is such a step. A step that is not a wrapper has its own execution when a pipeline, a `Parallel`, a `Map`, a Loop or a wrapper runs it. `WithPolicy`, `WithCache` and `WithAmendable` return wrappers. A decorator you write is never a wrapper, even when it embeds one. Match errors with `errors.Is` and `errors.As`, not text, and read the inner error from `StepError.Err`.
- `Map`, `MapCollect` and `Parallel` that a caller runs with `Run` or `RunCandidate` now return their own error as a `StepError`. It names them once, as a Loop's does. So `errors.As` finds that `StepError` first. `element 0: pipeline step "measure": boom` becomes `pipeline step "lengths": element 0: pipeline step "measure": boom`. A pipeline or a wrapper that runs them returns the same error as before. A step with another name that calls their `Run` now gets the `StepError`. A step with their name that runs in its own execution gets the error as it is. A decorator that embeds one of them and keeps its name is such a step. The rules for wrappers and own executions are those of the bullet above. Match errors with `errors.Is` and `errors.As`, not text, and read the inner error from `StepError.Err`.
- A `Map` or `MapCollect` can run outside a pipeline's own steps: directly, or by a decorator or another step that runs it. It now refuses a body that does not read the item key before any element runs. The error is the one `Build` gives, such as `pipeline step "each": body "loop" must read the item key "page"`. Before, the elements ran. Only `Build` checks the type the body reads the item as, so a run still converts the element to that type. Make the body read the item key.
- `Build` errors now say where a key that only a composite's nested views hold comes from. A Map's item reads `(Map "each" holds each element under it as int)` in place of `(step "each" writes it as int)`. A Loop's iteration key reads `(Loop "scan" numbers its iterations with it as int)`. Match errors with `errors.Is` and `errors.As`, not text.

#### Images

- Tool output and `ToolStep` arguments now cost a second encode when their JSON holds the exact shape of an image's summary. That is so also for a text-only value with that shape, such as a map. It applies when the type of the value can hold an `Image` or reach a `MarshalJSONTo`, as the `NewTool` doc says. The type of a value inside it counts too. The encode decides on the dynamic type, so an `any` that holds a text-only value does not count. So the `MarshalJSON` and `MarshalJSONTo` methods of the whole value then run twice.
- `Message` gains `Parts`. So the schema of a type that holds a `Message` gains a required `parts` property. That changes the request bytes of a `NewTool` whose `Args` holds one. It also changes the prompt and the response format of a `TypedPredict` whose `In` or `Out` holds one. A model must send `parts` as an array or as null. In the schema that a model follows, each part's `image` takes only null (`{"type":"null"}`), since JSON holds no image data. `Pipeline.Fingerprint` does not change. To keep the old schema, use a message type of your own without `Parts`.
- A `TypedPredict` whose `In` is a pointer to a struct checks its given `Signature.Inputs` as a struct `In` does. They must name exactly the JSON fields of the struct, so `Validate` and `Build` refuse inputs that v0.9.0 accepted. To migrate, list every JSON field of the struct in `Signature.Inputs`.

#### Test kit

- `gepatest.CheckChatClient` takes options (`CheckChatClient(t, client, options ...ChatCheckOption)`), so a variable of type `func(gepatest.TestingT, gepa.ChatClient) bool` no longer holds it. Call it directly or wrap it in a function literal.

#### Struct literals

- These structs gain fields, so unkeyed struct literals of them break: `PipelineSpec` and `agents.Agent` (`ToolMiddleware`), `Message` (`Parts`) and gepatest's `Call` (`Images`). `StepError` gains an unexported field, so an unkeyed literal of it breaks too. Use keyed literals. Callers cannot set that field. So a `StepError` from a step that ran with an iteration number never equals a literal under `require.Equal`. Compare it with `errors.As` and its exported fields instead.

### Added

#### Loop

- `Loop(name, body, until, LoopOptions{MaxIterations, Iteration})` runs a body step again until `until`, a typed condition on the state, holds. The body runs at least once and at most `MaxIterations` times, one iteration at a time. `Build` refuses a Loop without a cap (`MaxIterations` below 1), without `until`, or with a body that writes nothing.
- The Loop has its own state scope. Each iteration runs on its own view of the keys the body reads. A key the body reads and writes carries to the next iteration and starts from its `Default` or an earlier write. A `Default` is the usual seed. A `MergeRule` for an earlier write combines the seed with the Loop's value, which already holds it. To carry a key in a `Map` element, run the Loop in a nested pipeline whose `Defaults` seed it. Then make that pipeline's `NewProgramStep` the Map's body. `LoopOptions.Iteration`, when it has a `Name`, holds the number of the iteration, from one, in the body's view only. `Build` requires the body to read it as `int`, refuses a body that writes it, and refuses a key already in state.
- When `until` holds, the Loop commits the writes of that iteration. `MergeRule`s apply only to this commit.
- At its cap the Loop fails with a Permanent error that wraps the new `ErrMaxIterations` and commits nothing. An `OnError` transition with `errors.Is(err, gepa.ErrMaxIterations)` can route the run on. In a `MapCollect` it is the element's `MapResult.Error`.
- A failed iteration fails the Loop with an error that names the iteration and keeps the kind of the body's error. So `WithPolicy` around the Loop retries a Transient failure from the first iteration. The Loop then commits nothing, not its iterations' writes, tool memory writes or cached tool results. An error or a panic in `until` fails the Loop, a panic with the stack under `Details["stack"]`. Cancellation or a spent budget stops the Loop before the next iteration.
- Iterations see the tool memory writes and cached tool results of the iterations before them. The Loop commits them only when `until` holds: with its own execution, or with the step it runs in when a step calls its `Run`. Outside every step it commits the memory writes to its context's tool memory. It commits the cached results to the tool sessions that made the calls.
- `Run` refuses, before the first iteration, what `Build` refuses about the Loop itself. That is a missing cap or `until`, a nil body, a body with keys that are not valid and a body that writes nothing. It is also a body that does not read the iteration key or writes it. Only `Build` checks that the body reads the key as `int`, and a run converts the number to the type the body reads. `Run` also refuses a `State` that already exposes the iteration key, also through a wrapper, a `Parallel` or a `Map` element. It refuses a `State` that exposes no value for a key the body carries. When a caller runs the Loop, its error is a `StepError` that names it once. A step with the Loop's name that runs in its own execution gets the error as it is. A decorator that embeds the Loop and keeps its name is such a step. A step that is not a wrapper has its own execution when a pipeline, a `Parallel`, a `Map`, a Loop or a wrapper runs it. `WithPolicy`, `WithCache` and `WithAmendable` return wrappers. A decorator you write is never a wrapper, even when it embeds one. `until` must be safe for concurrent use.
- Each iteration is an execution of the body with its own usage, path `"<loop>.<body>"` and events. Its events, and those of the executions nested in it, carry `Attributes["iteration"]`. The nearest execution with the Loop's name carries `Attributes["iterations"]` once in its `StepFinished`. That is the Loop's own execution, or else that of a step with the Loop's name that runs it. A decorator that embeds the Loop and keeps its name is such a step. `StepAttributesFrom`, `gepatest.Call.Attributes`, traces and `gepatest.AssertTrace` see them, and `HTMLRunReport` shows "iteration N" and "N iterations". Both attributes pass through the run's `Redactor` under the Loop's iteration key. When it changes one or panics, events, traces and `HTMLRunReport` leave it out, so `AssertTrace` matches it by its absence. The Loop's error names the running iteration, so its number is public. The run does not remove that number from error text where a step reads the iteration key in the iteration. A pipeline that the iteration runs, at any depth, can take the number as an `int` input under the key's name. The run keeps the number there too. The Redactor treats every other value under that name as any other value, and the run removes its text. That includes a Default, a write, a Map item, another number, and the number as a string or a float. So does a copy of the number under another hidden key or in a detail. Reflection under `ProgramEvaluator` keeps the number in the same places. When another hidden value has the same text, the run still removes the number. It removes it from the events of the whole trace and from reflection for the whole example. `StepAttributesFrom` returns the values the step runs with. A `PerStepTokens` limit on the body counts every iteration.
- A Loop can be the From or To of a transition, a rewind target or the target of `WithAmendable`. A rewind starts it again at the first iteration. A Loop can also be the body of a `Map`, a `MapCollect` or another Loop. The Loop scopes its body's components as `"<loop>.<body>.<component>"`.
- `Pipeline.Fingerprint` covers each Loop's `MaxIterations`, iteration key and body. Pipelines without a Loop keep their fingerprint.

#### Tool middleware

- Tool middleware: `ToolMiddleware func(next ToolProvider) ToolProvider` wraps a tool, for example to limit, log, audit or fall back around its calls. Register it with `ToolRegistry.RegisterToolMiddleware(name, middleware)` and find it with `LookupToolMiddleware(name)`. Attach it by name, outermost first, with `PipelineSpec.ToolMiddleware` or `agents.Agent.ToolMiddleware`. Tools, chat middleware and tool middleware have separate names.
- In a pipeline the middleware wraps the calls of its `ToolStep`s and `Predict` steps. It also wraps those of a `Predict` in a nested run that has a `ToolPolicy` but no `Tools`. In an agent it wraps the bindings and the registry tools alike. A session that starts inside the run, such as an agent's or that of a nested pipeline with `Tools`, uses only its own tool middleware. The enclosing `ToolPolicy` still governs those calls.
- The middleware sees only the calls the session invokes, never refused or cached ones. Its context carries the run's tool scope, tool memory, `RunContext`, step path and budget. A retry inside it is one call, one record and one unit of `MaxCalls`. The session checks, caches and applies the result the middleware returns.
- Each call to `next` is an attempt that runs the tool once. An attempt belongs to the call whose context it carries. The first attempt of a call is the first attempt that carries its context. An attempt records its usage with `RecordUsage` and `RecordUnbudgetedUsage` as soon as it returns, as the session records a call without middleware. The call's record shows the usage of all its attempts.
- The middleware may return the result of one of its own call's attempts as it is. Any other result it returns must carry no usage, or the call fails. So a middleware that reuses a result across calls, such as a cache or a singleflight, must return that result without usage. The error of such a call keeps the kind of the error that the middleware returned. It is Permanent when the middleware returned no error or an unclassified error. Middleware that spends tokens itself records them with `RecordUsage` or `RecordUnbudgetedUsage`.
- The first attempt always runs. A later attempt fails with the context's cause when its context has ended. The run's budget refuses a later attempt as it refuses a model call. It refuses one when the tokens of the run or the step exceed a limit. It also refuses one when the run has reached `MaxDuration` or has already failed with a budget error. A spent `MaxModelCalls` does not refuse an attempt.
- An attempt fails when its context carries no call of the tool, and when its call has already returned. When the middleware returns, the call cancels the attempts that still run and waits for them. So a timeout in middleware cannot bound a tool that ignores its context.
- An attempt turns a panic of the tool into the error `tool panicked: ...`, with the stack in its step details. It fails output that is not valid JSON and provenance that is not valid with the session's errors. So the middleware sees these failures and can fall back.
- `Build` applies the middleware to each tool the steps name. `Agent.Validate` applies it to each tool of the agent. Both fail on middleware that panics, returns nil or changes a tool's schema. They also fail on an unknown name, a repeated name, and `ToolMiddleware` without `Tools` or a `ToolRegistry`. A run applies the middleware to each tool on the tool's first call. If that fails, only the calls to that tool fail.
- `ToolRegistry.WrapTool(provider, names...)` applies tool middleware to one provider. The result keeps the provider's schema, `Validate` method and Go types. So a registry takes it, `Build` checks a `ToolStep` that names it, and `gepatest.CheckToolProvider` checks it. Its result carries no usage, since the attempts recorded it. With no names `WrapTool` returns the provider itself.
- Tool middleware names enter no fingerprint, record, event, trace or report. A pipeline or agent without tool middleware runs as before.

#### Images

- Image parts in chat messages: `Image` and `Part`. Build an `Image` with `NewImage(data)` from PNG, JPEG or WebP data of at most `MaxImageBytes`. That is 3,932,160 bytes, whose base64 is exactly 5 MiB, since Claude's 5 MB per-image limit applies to the base64. A `Part` holds a text or an `Image`. A user `Message` carries them in `Parts`, after its `Content`. `NewImage` reads the media type from the first bytes and checks the start of the structure that follows them. That is a PNG's IHDR chunk, a marker after a JPEG's start of image, or a WebP's VP8, VP8L or VP8X chunk. Then it copies the data and hashes it once. The providers also limit a whole request, such as about 20 MB of inline data for Gemini, as the `MaxImageBytes` doc says. An `Image` is immutable and gives `MediaType`, `Size`, `Data` (a copy), `SHA256` and `Validate`. `Part.Validate` requires exactly one of a text that is not blank and a valid image. Errors from `NewImage` and `Image.Validate` match `ErrInvalidImage`. `ErrImagesUnsupported` marks images sent to a model that cannot take them.
- An `Image` never shows its data outside a provider request. `String`, every `fmt` verb and `MarshalJSON` give a summary of its media type, size and SHA-256 digest. The summary is `{"media_type":"image/png","size":48213,"sha256":"..."}`, and `null` for the zero `Image`. `UnmarshalJSON` refuses every value but `null`, since the summary holds no data. The data is behind pointers. So where `fmt` cannot call the methods, such as for `%p` or in an unexported struct field, a print shows an address.
- `Field.Type` `"image"` on a signature input, whose `GoType` is `Image`. An output with it fails `Signature.Validate` and `Signature.JSONSchema` with the same error.
- The OpenAI, Claude and Google chat clients send image parts as base64 data. OpenAI gets an `image_url` part with a data URL, Claude a base64 `image` block and Google an `inlineData` part. A request with parts on a message that is not a user message fails with a Permanent error before the client sends it. So does a request with a part that fails `Part.Validate`. When a provider error quotes the request, the clients replace the base64 data of its images. They do this in the returned error and in the log record. They replace each part of the data of at least 32 base64 characters. Such a part can be the whole data, an echo cut short or a slice from the middle. It may stand next to other text or an escape. The clients read a base64 character that JSON escapes, as in `\/`, `\u002B` (as .NET writes '+'), `\u002f` or `\u003D`. They also read one that JSON held in a JSON string escapes twice, as in `\\/`, `\\\/` or `\\u002B`. They read one that a URL escapes too, as in `%2B`, `%2F` or `%3D`, or escapes twice, as in `%252B`. They also read an HTML numeric entity, as in `&#43;` or `&#x2B;`. The search is exact. A character goes if and only if it is in a part of the data of 32 characters or more. So data of fewer than 32 characters, an image of fewer than 24 bytes, stays. The search indexes the error's text, not the images. It indexes at most 1,048,576 characters at once and reads the images once for each such chunk. So its index stays at about 70 MB for an error of any length. The scrubbed text that it returns grows with the error. It takes time linear in the error, plus the images once for each chunk. The clients send requests without parts as the same bytes as before, which new byte goldens of the request bodies check. Claude's OpenTelemetry content mode exports images as base64 data in its spans.
- `Predict` and `ChainOfThought` take images in their inputs, at any depth. A call with images chats, also without tools or middleware, and then needs no `ToolRegistry`. Its one user message has an empty `Content`. Its `Parts` hold, for each distinct image by digest, the text `[image N]` and then the image. The last part is the prompt. A `ChatClient` or `ChatMiddleware` that reads only `Content` sees no prompt in such a call, so it must read the text parts too. The repairs continue the same chat, so the images stay in its first message, and `Predict` does not use `RepairLM`. A model that cannot chat, such as `providers/pi` or a `RetryingLanguageModel` around a plain generator, fails the run before any call. The error is Permanent, matches `ErrImagesUnsupported` and names the signature, the input and the model's type. A negative `MaxToolTurns` fails such a call too, with a Permanent error that names the signature. Inputs without images send the same request as before, which a new byte golden of `BuildPrompt` checks.
- `BuildPrompt` writes each image as the string `"[image N]"` in the input JSON, numbered from 1 in encoding order. An image that comes again, by digest, keeps its number. The zero `Image` is `null`. After the JSON it adds the line `Each "[image N]" input is the image attached above with that label.`
- An input with `Field.Type` `"image"` must hold an `Image` from `NewImage` at run time. Without a model that can chat it fails `Validate`, and so `Build`, with a Permanent error that matches `ErrImagesUnsupported`. A negative `MaxToolTurns` fails `Validate` too. `Predict.ProgramSignature`, `ChainOfThought.ProgramSignature` and `TypedPredict.ProgramSignature` give it the input type `Image`. So `Build` refuses a step that reads it from a key of another type. A demo that holds an `Image` fails `Validate`.
- `TypedPredict` derives the `Type` `"image"` for an `In` field of type `Image`. An `Image` field tagged `omitempty` or `omitzero` is an optional image. It keeps the schema `{}`. A zero `Image` there sends no image. The prompt leaves it out (omitzero) or writes null (omitempty). Other fields that hold images, such as `*Image` and `[]Image`, keep the schema `{}` too. The input type of an optional image is `*Image`. So in a pipeline a step reads it from a `*Image` key, nil for no image, and a required `Image` field from an `Image` key. A given `"image"` input on such an optional field is optional too. A given `"image"` input must name an `Image` field when `In` is a struct or a pointer to one. Otherwise `In` must be an empty interface, or a map whose values are `Image` or an empty interface, such as `Prediction`. Pointers to these work too, as do map values behind pointers, such as `*map[string]Image` or `map[string]*any`. Only an input of the `Type` `"image"` needs a model that can chat to pass `Validate`. A run checks every other input against its value, as `Predict` does. So a field of a type such as `*Image`, `[]Image` or `[]Message` passes `Validate` with any model. A run whose inputs hold an `Image` needs a model that can chat and a `MaxToolTurns` that is not negative. Without a model that can chat, it fails before any call with a Permanent error that matches `ErrImagesUnsupported`. With a negative `MaxToolTurns`, it fails before any call with a Permanent error that says so. `Run`, `RunTyped` and `RunCandidate` send `In`'s images as images. A reply cannot carry an image. So an `Out` field of type `Image` fails `Validate`. A reply that gives an `Image` elsewhere in `Out`, such as in a `Message` part, a value other than null fails to decode with `ErrInvalidImage`. It goes through the repair loop like any other invalid reply, and the error names nothing of the reply.
- gepago checks images against values, not types. `Build` refuses an input of the `Type` `"image"` without a chat model, and an output with that `Type`. It also refuses a `ToolStep` read whose type is an `Image`, or a chain of pointers, slices, arrays and map values that ends at one. Tools follow two rules. `ToolRegistry.Register` refuses a `NewTool` whose `Args` no JSON value can decode into, because the decode requires an `Image` there. An example is a field of the type `Image` without `omitempty` or `omitzero`, also in a nested struct or an array. `Register` cannot see a decoder that a type takes from an embedded `Image`, such as `struct{ Image }`. So it accepts `Args` that require such a type, and their calls fail. Every other `Image` fails at call time, when a value holds one. That covers every `Out`. Apart from these refusals, a type that holds an `Image` in a struct field works as in v0.9.0 while its values hold no image. `Message`, `Part`, `ChatRequest` and `ChatResponse` are such types.
- `ToolStep` arguments travel as JSON. So a read whose value holds an `Image` from `NewImage` fails the step with a Permanent error. The error names the key and the Go type of its value only when that value alone holds the image. Otherwise, such as for a `MarshalJSONTo` that encodes an `Image` only inside another value, it names no key. A zero `Image` encodes as `null`. A type that embeds an `Image` or a `*Image`, or that writes its own JSON, encodes as `json.Marshal` writes it. So the tool gets at most the image's summary, and never the image. But a `MarshalJSONTo` that encodes an `Image` it holds through its encoder still fails. A `MarshalJSONTo` that encodes an `Image` apart and then writes the result as text passes, and the tool gets the summary as text. The JSON of all the arguments can hold the full summary of an image elsewhere. Then that `MarshalJSONTo` fails too, and the error names its key.
- Tool arguments and output travel as JSON, and the JSON form of an `Image` holds no image data. So an `Image` from `NewImage` in the output of a `NewTool` fails the call with a Permanent error. The error names the tool and the Go type of the output. The encode finds an `Image` where `json.Marshal` encodes one, also in an interface value such as `any`. It skips unexported fields and fields tagged `"-"`. A type that embeds an `Image` or a `*Image`, or that writes its own JSON, encodes as `json.Marshal` writes it. So the model gets at most the image's summary, and never the image. But a `MarshalJSONTo` that encodes an `Image` it holds through its encoder still fails. A `MarshalJSONTo` can first encode an `Image` apart, such as with `jsonv2.Marshal` and the options of its encoder. When it then writes the result as a string or in another form, the model gets the summary as text. That passes unless the JSON of the whole output holds the full summary of an image elsewhere. The second encode then refuses that `Image` too. A zero `Image` encodes as `null`. The encode of tool output and `ToolStep` arguments calls `json.Marshal` once and returns its error as it is. That is all it does for a type that cannot hold an `Image` or reach a `MarshalJSONTo`. Otherwise it scans the JSON for the full summary of an image. Only a value whose JSON holds one costs a second encode, also when the value only looks like a summary. So a `MarshalJSON` runs once, unless the JSON of the whole value holds such a summary. `JSONSchemaFor` gives an `Image` and a `*Image` the schema `{"type":"null"}`, since only null decodes into one. Arguments that give an `Image` of `Args` a value fail the call with `ErrInvalidToolArguments` and `ErrInvalidImage`.
- `Key.Get` converts between `Image` and `*Image`, and into structs, slices, maps and empty interfaces (`any` and named ones) that hold images. It puts each `Image` of the stored value back at its place in the JSON form. `Key.Get` and `Predict` do not find an `Image` behind a type's own `MarshalJSON`. `Predict` sends no image for it, and `Key.Get` into an `any` gives its summary as a map. gepa leaves out an `Image` in an unexported field entirely, with no summary. A value that only looks like an image's summary, such as a map equal to it, keeps its type. A summary in an `Image` position where the stored value held no image fails. The error matches `ErrInvalidImage`. For a state value it names the digest only when that is 64 lower-case hex digits. For a model reply, tool arguments or tool output it names nothing of the value. Other types decode as before.
- Traces, the HTML report, `MapResult`, reflection records, `WithCache` default keys and the optimiser's config fingerprint hold an image's summary. So the same image gives the same key and fingerprint, and another image another one. `Pipeline.Fingerprint` holds no values. A `Redactor` gets the `Image` under its key. When it changes a value, gepa removes from error messages the `String` text and JSON summary of each image the value holds, at any depth. It keeps them for an image that the redacted value still holds.

#### Test kit

- `gepatest.CheckToolMiddleware(t, middleware, options...)` is a contract test for tool middleware. It runs the middleware in pipelines around a scripted tool. The cases make two calls with the same arguments at once and a third after them. In other cases the tool fails, panics or returns bad output once. The check also cancels runs during an attempt, and while a call waits inside the middleware. It reports middleware that `Build` or a run cannot wrap the tool with, and middleware that panics. A report gives only the type of a panic value. It reports an attempt with a context of no call or of another run. It reports an attempt that reaches the next of another run or of an earlier wrap of the tool. It reports an attempt with the context or the ID of another call. It also reports an attempt that starts after its call returned. It reports a result with usage that no attempt of its own call returned, and attempt usage that the run's usage collector misses. It reports a run that does not return within five seconds after the check cancels it, and then it stops. It also stops at a `Build` that does not return within the deadline and five seconds. It stops at a run that cannot wrap the tool because the middleware does not return. It fails middleware that makes no attempt in any case, and it logs each other case without an attempt. The check cancels a case after ten seconds. The options `MiddlewareToolName`, `MiddlewareArguments`, `MiddlewareScope` and `MiddlewareDeadline` set the tool's name, the arguments and scope of the calls, and that deadline. The check misses an attempt with another call's context when the middleware changes the ID. It misses an attempt that starts after the check ends. It reports an attempt with the context of a call of another run on both runs, since either run's middleware can have made it. It does not report a late attempt in a run that the check cancelled, or on a context that the middleware ended itself. It does not find leaked goroutines or usage that the middleware records twice.
- `gepatest.PNG(label)` returns a small, valid, deterministic PNG with a distinct digest per label. It stores its pixels uncompressed, so its bytes do not change with the Go toolchain. `FakeGenerator.Chat` refuses invalid parts with `ErrInvalidChatRequest`, and parts on a message that is not a user message too. It records the images of a call in `Call.Images` and adds text parts to `Call.Prompt`. `CheckChatClient` takes `ChatImages()`. With it, the check also requires a client to refuse invalid parts with a Permanent error and no usage. The client must also answer a request with a PNG. Without it the check sends no parts.

### Fixed

- A step with another name can run a `Map` or `MapCollect` through `Run` with its own `State`. The Map no longer adds its `"failed"` attribute to that step's `StepFinished`. Only the nearest execution with the Map's name reports it. That is the Map's own execution, or else that of a step with its name that runs it. A decorator that embeds the Map and keeps its name is such a step.
- The context that an observer gets no longer carries where the observed execution runs. That is its visit, its `Map` element and its Loop iteration with the iteration numbers. It is also the end of an execution that a top-level `WithPolicy`, `WithCache` or `WithAmendable` step holds back until the pipeline commits the result. So a run that an observer starts with that context is a run of its own. Before, such a run could report the end of its step after its own end. That happened during a failed commit of a top-level wrapper. It also happened at the start of a cache hit of a `WithCache` step that is a top-level wrapper or is inside one. A run that an observer started at the end of such a cache hit never reported the end of its step. Its trace then held a step without an end. The context keeps its other values, such as the tool scope. As before, it carries neither tool memory, usage collection nor the other values that the `PipelineObserver` doc names.

## v0.9.0

`Pipeline` can run a real extraction flow: one transition engine with forward skips and bounded rewinds replaces the control-flow combinators, `Map` fans out over lists known only at run time, tool calls carry the caller's scope and usage billed elsewhere, and state decodes with `encoding/json/v2` on Go 1.27.

### Breaking changes

#### Toolchain and decoding

- Both modules require Go 1.27.1, and `GOEXPERIMENT=nojsonv2` is not supported. Upgrade Go.
- State values, `TypedPredict` replies and `NewTool` arguments decode with `encoding/json/v2`, which refuses input v0.8.0 accepted: duplicate object names in a raw JSON (`json.RawMessage`) state value (`TypedPredict` replies and `NewTool` arguments still keep the last), times that are not strict RFC 3339 (such as `,` before the fraction or a `+24:00` offset), base64 with line breaks, lone UTF-16 surrogate escapes in `,string` fields, invalid UTF-8 or lone surrogates inside a `json.RawMessage`, and map keys that decode to the same key (`"1"` and `"01"`). Fix such data where it is produced.
- A struct whose definition v2 refuses fails every decode, even of an object without the faulty field, and `JSONSchemaFor`, `NewTool` and `TypedPredict` (given `Inputs` included, at any depth) refuse it up front: an unexported field with a json tag, two fields with one JSON name, an unnamed embedded non-struct, an embedded struct with tag options or marshal methods, a struct without exported fields, a malformed or repeated tag option, a single-quoted name, `json:"-,"`, any option but `omitempty`, `omitzero` and `string` (`embed`, `inline`, `case:…`, `format:…`, misspellings), and `,string` on anything but a boolean, number or string (or an unnamed pointer to one) or on a type with its own unmarshal method. Remove the tag or option, or rename the field.
- A json tag name that `encoding/json` rejected, such as `temp°C`, is now the field's JSON name for decoding and encoding, as the schema already said; v0.8.0 refused such members and wrote the Go field name. Rename the tag if you relied on the Go name.
- A type with `UnmarshalJSONFrom` decodes through it and gets schema `{}`, so a struct embedding `json.Number` decodes from a bare number and refuses `{"Number":"5"}`. A `,string` `json.Number` refuses text that is not a JSON number (`"0x10"`, `"01"`, `"1."`, `"-Inf"`, `"5 "`). Send the JSON form.
- Decoding error text changed: errors from custom unmarshalers and times are wrapped as `json: cannot unmarshal … of type T: <err>`, paths name the innermost struct and the JSON field names, `,string`, `TextUnmarshaler`, `Duration` overflow and `*T` messages read differently, and with several faults the one reported can differ (a type error before a renamed field now reports the missing field). A stored Go map with float keys now converts, and bool, pointer and struct keys fail with another error. Metric text for map keys that encode alike is `{"a":1,"a#2":2}`. Match errors with `errors.Is` and `errors.As`, not text.

#### Tools

#### Pipelines and control flow

- `StepPolicy.OnError`, `ErrorAction`, `OnErrorFail`, `OnErrorSkip` and `OnErrorFallback` are removed: a step that still fails after its last attempt fails the run. For `OnErrorSkip`, add an `OnError` `Transition` from the step to the next one, or to `gepa.End` for the last step, with a `Default` for each write a later step reads. `Fallback` replaces `OnErrorFallback` but does not fall back on a Permanent error, which `OnErrorFallback` did; to fall back on any error, put the secondary step right after the step and add `{From: step, OnError: true, To: secondary}` and `{From: step, To: next}`, where `next` is the step after the secondary or `gepa.End`, with a `Default` for each of their writes a later step reads. A step inside a `Parallel` or a `Map` body has no equivalent, since transitions name top-level steps only: lift it to the top level, or handle the error inside the step.
- `RetryPolicy.RetryIf` is removed: a `StepPolicy` retries Transient errors only. Wrap retryable errors with `TransientError`.
- `KeyDefault` is now `Default`, which `DefaultValue` returns. Defaults seed state before every run's first step, so steps see them and `Run` returns those no write replaced; a `MergeRule` never merges a write with a default; and `Build` refuses only a default that no step reads or writes. Rename the type, and drop defaults you do not want in the output.
- `Branch` and `Fallback` return a `Flow` of top-level steps and transitions, which cannot nest inside `Parallel`, `WithPolicy`, `WithCache` or `Map`. Add it with `spec.Add(gepa.Branch(...))`.

Arms and a Fallback's steps may not write, so a later step that reads their writes needs a `Default`. Rename `OnStep` scripts and expectations, and add the defaults.
- A Branch's name may not be a pipeline input or another step's write, and `Build` refuses steps named `$end` or `$fail` and a `PerStepTokens` entry that names a Branch or Fallback. Rename them, and budget the arms or steps instead.
- `Fallback` fails with the secondary step's error only; v0.8.0 joined both errors. Read the primary's error from its event or trace.
- The pipeline fingerprint now covers transitions, `MaxVisits`, amendable keys and each `Map`'s keys and `MapOptions`, so a v0.8.0 artefact no longer loads once its pipeline uses them, as `Branch`, `Fallback` and the migrations of `OnErrorSkip` and `OnErrorFallback` do; a pipeline that uses none keeps its fingerprint. Retrain for `Branch` and `Fallback` anyway: the old candidate keys of their arms and steps are ignored.
- These structs gain fields, so unkeyed struct literals of them break: `PipelineSpec` (`Transitions`, `MaxVisits`), `ToolCall` (`Scope`), `Provenance` (`Kind`, `ID`), `ToolResult` and `ToolCallRecord` (`UnbudgetedUsage`), `UsageSpan`, `RunFinishedEvent` and `PipelineTrace` (`Unbudgeted`), `StepStartedEvent` (`Attributes`), `StepFinishedEvent` (`Attributes`, `Unbudgeted`), `StepTrace` (`Attributes`, `Transition`, `RewindRejected`, `Unbudgeted`), and gepatest's `Call`, `ExpectedStep` and `ExpectedTrace`. Use keyed literals.

#### Observability

### Added

- Transitions: `Transition{From, OnError, When, To, Amend, Accept}` in `PipelineSpec.Transitions`, with `End`, `Fail`, `PipelineSpec.MaxVisits` and `ErrMaxVisits`. After a top-level step finishes, the first matching transition skips forward, ends or fails the run, or rewinds to the same or an earlier step and runs the range again, bounded by the target's `MaxVisits`, one range at a time. `Build` checks them in one pass over the transitions and one over the steps.
- Guaranteed keys: a step a transition skips over, or one with an `OnError` transition forward, may not write, and `Build` refuses a later read of its writes unless the key has a `Default`.
- Rewinds: `WithAmendable(step, keys...)` declares the keys a rewind's `Amend` may set for the target's next visit only, never committed; `Accept(prev, next)` keeps the new visit or restores the old one. Every visit's usage counts.
- `Flow` and `PipelineSpec.Add`; `Branch` and `Fallback` are built from ordinary steps and transitions.
- `Map` and `MapCollect` run a body once per element of a list known only at run time, each on its own view, at most `MapOptions.MaxConcurrency` at a time and refusing more than `MaxItems`. `Map` fails fast and commits nothing; `MapCollect` writes a `MapResult{Index, Value, Error, Usage, Duration}` for every element, unless an element hits a `Budget` error or the run's context ends, which fail the step. Elements share the run's budget and tool scope.
- Events: `Attributes` on `StepStartedEvent`, `StepFinishedEvent` and `StepTrace` (`visit`, a Map element's `index`, a Map's `failed`), `StepAttributesFrom(ctx)`, and `TransitionObserver` with `TransitionTakenEvent` and `RewindRejectedEvent`, which `RecordingObserver` records as `StepTrace.Transition` (`TransitionTrace`) and `StepTrace.RewindRejected`. The run report shows visits, elements, transitions and rejected rewinds.
- Tool scope: `WithToolScope(ctx, scope)` sets an opaque scope, such as a tenant, on every tool call of a run; a tool reads it with `ToolCall.ScopeAs[T]()`, or with `ToolScopeFrom(ctx)` in a `NewTool` function or an agent `ToolBinding` handler. gepago never inspects or marshals it in-process; it must be JSON-marshalable when calls cross a process boundary.
- Unbudgeted usage: `ToolResult.UnbudgetedUsage` and `RecordUnbudgetedUsage` record usage a run reports but no budget counts. `UsageSpan`, `StepFinishedEvent`, `RunFinishedEvent`, `StepTrace`, `PipelineTrace` and `ToolCallRecord` carry it apart from `Usage`.
- `Provenance.Kind` and `ID` name a protected resource for audit, beside `Source` and `Detail`, checked by `Provenance.Validate`.
- Test kit: `gepatest.CheckToolProvider(t, provider, options...)`, with `ToolArguments(...)` and `ToolScope(...)`, checks a tool's schema, its refusal of invalid arguments, panics, usage, an ended context, valid calls, a cache hit in a caching `ToolSession` and concurrent calls, and `CheckChatClient(t, client)` checks a chat client's refusal of requests no provider accepts, panics, usage, an ended context, a valid request, the same request sent again reporting the same `PromptTokens` when a prompt cache may answer it, and concurrent requests, so you can prove your adapters. `FakeGenerator.OnVisit` and `OnElement` script one visit or one Map element (`OnElement` does not match the calls of a pipeline an element runs; script those by step path), calls record their `Attributes`, and `ErrInvalidChatRequest` marks a chat request no provider accepts. `AssertTrace` checks attributes and matches Map elements by index, giving the steps of a pipeline an element runs that element's index.
- Example `examples/map_reduce`: a deterministic pipeline with two forward skips, `MapCollect`, a `TypedPredict` reducer that rewinds once with an amendment, and a tool that reads the scope.

A nested run's values pass through every enclosing Redactor too, so its observers see outer-redacted values, and spans whose `ParentID` belongs to an enclosing run they do not observe. A run with a Redactor and no observers still redacts every value, for the runs nested in it. With a Redactor, `ProgramEvaluator` redacts each item's `Output` and `SideInfo`, `reads` included, while the metric scores the real values.
- Run context: `RunContext{RunID, ParentRunID, TraceID, Attributes}`, `WithRunContext` and `RunContextFrom`. A run keeps the caller's trace ID and attributes, takes the caller's run as its parent and gets a fresh `RunID`, so nested pipelines form one trace. Events and `PipelineTrace` carry the `RunContext`, a run's span ID is its `RunID` and its trace ID is the `TraceID`, and the run report has a Run context section. Observer contexts carry neither the run's `RunContext` nor its `ToolMemory`, so an observer's own work is independent of the run. Provider `Config.Logger` writes one record per model call with the run context, a call that panics included.
- Artefacts: `Pipeline.Fingerprint` from step names, keys and types, the `Fingerprinter` interface, `ProgramArtifact.Fingerprint`, `CompiledProgram.Artifact` and `FingerprintMismatchError`. A `ProgramVersion` stated by both the artefact and `LoadCompiledProgramVersion` or `LoadCompiledVersion` stands in for the fingerprint. The TypeScript `ProgramArtifact` has an optional `fingerprint`, which `parseProgramArtifact`, `loadProgramArtifact` and `saveProgramArtifact` keep and reject when it is not a string.
- `DefaultReflectiveDatasetBuilder` names the failing step of an invalid output and carries its `StepError.Details` and the values it read.
- WASM: `gepagoWasm.start` takes the `pipeline.run` operation, which runs a compiled pipeline programme as `compile` runs it; `runCompiled` uses it.
- Test kit: package `gepatest` with `FakeGenerator`, a `Generator`, `StructuredGenerator` and `ChatClient` that answers from reply scripts keyed by step path or name, prompt substring or a default, each reply with its own text or tool calls, usage, finish reason and error, records every call and lists the calls no script answered (`Unmatched`), whose error a step policy's fallback or skip can hide; and `AssertTrace`, which checks a `PipelineTrace`'s step executions (path, attempt, failure, error text or kind, cached and skipped flags, usage, tool calls) and the run's outcome and usage, checks that executions which did not overlap in time ran in the order listed (different steps of a `Parallel` are unordered), and reports a diff. `StepPathFrom(ctx)` returns the path a running step has in traces. `StepTrace` and `PipelineTrace` record `Failed`, set even when the error's message is empty, and `StepTrace` and `StepStartedEvent` name the step of a `Parallel` an execution belongs to in `Lane`, shared by its retries and its policy's fallback.

### Fixed

- A provider call that fails after spending tokens returns that usage with its error, so it is recorded exactly once, also when calls run concurrently; v0.7 read it back through `LastUsage`.
- `Predict` no longer sends a truncated reply through the repair prompt.
- `RetryingLanguageModel` no longer retries permanent errors or a call whose context has ended.
- Google provider error messages no longer include the API key.
- A panicking agent tool no longer crashes the agent run.
- A WASM async job (`compile`, `runAgent`, capability jobs) that fails before its first host call reports its error instead of "completed with an unexpected job id": the module now calls `onComplete` from a later JavaScript task, after `start` has returned the job id.

## v0.7.0

### Breaking changes

- `UsageReporter` implementations must reset their usage when each call starts. `Predict`, `LLMJudgeMetric` and `RetryingLanguageModel` now record usage for calls that return an error, so an implementation that keeps the previous call's usage counts it twice.
- `RetryingLanguageModel` has pointer receivers and must be used as `&gepa.RetryingLanguageModel{...}`. `LastUsage` now sums every attempt of the most recent call.
- `ProgramEvaluator` scores examples that fail with `ErrInvalidOutput` as zero instead of returning an error.

### Added

- Typed `PipelineSpec`/`Pipeline` with `Key[T]` state: build-time read/write and type checks, run-time type enforcement, copy-on-boundary values, read-only and strictly declared inputs, merge rules, signature-checked programme steps, strict decoding with `Validate`, and partial state with `StepError` details (including recovered panics) on failure. `PipelineProgram` remains for the WASM compile bridge.

### Fixed

- `ProgramEvaluator` returns usage alongside evaluation errors, so the optimiser ledger keeps tokens spent before a failure.
- The WASM compile model resets its usage on every call path.
- Crucible reports a subject's error before checking output size, so a partial output no longer hides it.
